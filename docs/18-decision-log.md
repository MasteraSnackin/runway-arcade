# Decision Log

## Purpose

This document records major product and architecture decisions for the MVP. Add new decisions here when the project changes direction.

## ADR-001: Keep MVP Read-Only and Simulation-Only

Date: 2026-07-03

Status: Accepted

Decision:

The MVP must not write to Xero, send payments, or send customer chases. Approvals only create simulated local state and audit records.

Rationale:

- The preview explicitly states "simulation only" and "no writes to Xero".
- Financial actions carry high risk.
- A read-first demo is enough to prove product value.

Consequences:

- The product can be demonstrated safely.
- Future write support requires a separate product, compliance, and engineering decision.

## ADR-002: Use a Xero Adapter Boundary

Date: 2026-07-03

Status: Accepted

Decision:

All finance calculations should consume normalised data through a `FinanceDataAdapter`, not direct Xero SDK response objects.

Rationale:

- The preview uses demo data but shows a live Xero path.
- A stable adapter allows fixtures and live OAuth data to be swapped.
- Domain calculations remain testable.

Consequences:

- Extra mapping code is required.
- UI components should not know whether data is demo or live.

## ADR-003: Use Shared Finance Calculations for Dashboard and Co-Pilot

Date: 2026-07-03

Status: Accepted

Decision:

Dashboard cards and AI tools must call the same calculation helpers.

Rationale:

- Users will lose trust if the co-pilot says different numbers from the dashboard.
- Shared helpers make calculations testable and auditable.

Consequences:

- Calculation changes need tests.
- Co-pilot tools return structured outputs rather than free-form calculations.

## ADR-004: Evidence Cards Must Be Rendered Through a Whitelist

Date: 2026-07-03

Status: Accepted

Decision:

Evidence cards should be generated by a controlled renderer that exposes only approved labels and values.

Rationale:

- The preview includes a self-test for internal field leakage.
- Raw fields such as `expectedInCents` are useful internally but poor user-facing content.
- The AI should not decide which hidden fields to reveal.

Consequences:

- Every tool result needs a display mapping.
- Adding a new tool requires evidence renderer updates.

## ADR-005: Store Money as Integer Minor Units

Date: 2026-07-03

Status: Accepted

Decision:

Money should be stored and transported as integer pence, with formatted display strings generated at the UI boundary.

Rationale:

- Avoids floating point errors.
- Makes audit and exports predictable.
- Aligns with common finance system practice.

Consequences:

- API fields need clear names such as `amountCents`.
- UI formatters are required.

## ADR-006: Use Query Params for Scenario State

Date: 2026-07-03

Status: Accepted

Decision:

Scenario state should be represented in the URL, for example `?scenario=cash_squeeze`.

Rationale:

- The preview uses scenario URLs.
- Share links need to preserve demo state.
- Judges and users can reload a specific scenario.

Consequences:

- Scenario IDs are part of the contract.
- Unknown scenario IDs need safe fallback behaviour.

## ADR-007: Treat AI as an Orchestrator Over Bounded Tools

Date: 2026-07-03

Status: Accepted

Decision:

The co-pilot may choose or explain tool results, but finance data access and calculations must be performed by bounded tools.

Rationale:

- The preview shows tool-call style responses.
- Bounded tools improve trust, reproducibility, and safety.
- Raw Xero data should not be handed to a model without minimisation.

Consequences:

- Tool schemas must be maintained.
- Unsupported prompts need safe fallback responses.

## ADR-008: Keep Xero Scope Names as Implementation-Time Checks

Date: 2026-07-03

Status: Accepted

Decision:

Documentation should link to Xero's current scope guidance and avoid treating guessed scope lists as final.

Rationale:

- Xero introduced granular scopes in 2026.
- Scope requirements can change by endpoint, app creation date, and migration state.
- Requesting too much access weakens trust; requesting too little breaks integration.

Consequences:

- Scope verification is a release checklist item.
- Insufficient-scope errors need clear handling.

## ADR-009: Append-Only Audit for Production

Date: 2026-07-03

Status: Proposed

Decision:

Production audit events should be append-only. User-facing clear actions should hide or archive records only where policy permits, not physically delete compliance data by default.

Rationale:

- Finance actions require traceability.
- Simulated approvals are already central to the MVP.
- Production writes would require stronger audit guarantees.

Consequences:

- Retention and deletion policy must be defined.
- UI clear behaviour may differ between demo and production.

## ADR-010: No Production Writes Without Separate Approval

Date: 2026-07-03

Status: Accepted

Decision:

Production write functionality is out of scope until explicitly approved.

Rationale:

- The current MVP demonstrates value without writes.
- Writes introduce OAuth scopes, permissions, audit, error recovery, and compliance risk.
- Invoice chases and payment actions affect real business relationships.

Consequences:

- Future roadmap can include writes, but they need a separate design.
- `ENABLE_XERO_WRITES` should default to false.
